The problem

A car build lives in forum threads, saved tabs, receipts and screenshots. Nothing ties a part to the exact car, what it cost, or the people building the same car.

I wanted one home for the car, the parts, the money spent and the community around it.

What was hard to build

Garage

Year, trim and engine have to be exactly right. The picker refuses cars that never existed, and members can correct anything the catalog gets wrong.

Smart Add

One box takes one part, a whole list, a link or a photo of the box. The work is turning messy input into the exact part, price and seller, with no forms to fill out.

Apollo chat

An assistant that already knows your car and your build. Answers are based on the member's own car, with a quick mode and a deeper one that searches the live web.

Command Center

The home screen. I had to choose the one next action to put first and keep everything else one tap away.

Community and clubs

Builds are public by default, and members can make theirs private. Clubs shipped on September 17, 2026.

OBD-II

Built, in testing

Reading the car's own data over Bluetooth. It hasn't been tested with a real adapter yet, so I'm not making claims about live data.

Where it runs

One web app, plus native shells on iPhone (Swift) and Android (Kotlin). One codebase means a fix ships everywhere at once.

The tradeoff is that some native features, like push notifications and age signals, need a small bridge on each platform.

The AI, engineered

Code first, AI last

Smart Add tries the cheap, certain steps before any model runs: a direct link, the parts catalog, a cache, then a shopping search. AI only handles what's left, and a typed list with prices and sellers is read with no AI at all.

Grounded in the member's car

Before Apollo chat answers, it reads the owner's actual build through a tool, with at most two tool rounds per reply. The instructions are put together on the server, and conversations aren't stored with the AI provider.

Fresh only when it matters

Quick answers search the web only when a question needs current facts. If search is unavailable, the chat still answers from what it knows.

Caching with rules

Shopping results are kept for 6 hours, web searches for a day, and AI readings of a part or a photo for 30 days. Only cleaned-up queries are cached, and a photo's cache keeps what was found in it. The image itself isn't kept.

One door for every model call

Every call to a model goes through one module. Answers are forced into fixed schemas so code can check them, and behavior is tested against the live service as well as its documentation.

Decisions and tradeoffs

One app in native shells

I'm one builder shipping to two stores, so I wrapped one web app in native shells and didn't build it three times. The cost is a little less native feel. Google Play went live on September 8, 2026, and the App Store approved it on September 13, 2026.

A push bridge for iPhone

The iPhone shell can't use web push, so on September 14, 2026 I built a native bridge to Apple's push service. Members get the same notifications on both platforms.

Schema as files

Every database change is a migration file, 341 of them, each applied with the release that needs it.

Tested before it ships

The test suite

4,391 tests in 440 files were passing on October 11, 2026. They guard the project's rules, like every member write going through the content filter.

Beyond unit tests

Lint with a cap on warnings, and three validators that read the whole codebase for broken rules before anything ships.

The release path

Tests, lint, the validators and a full build run before every signed-off commit. A push to main is a production deploy, so nothing reaches main without passing.

The systems behind it

A photo privacy pipeline

Every uploaded photo goes through a pipeline before anyone else can see it. It finds license plates, faces, VINs and addresses and blurs them, strips location and camera data, and stores the result privately behind links that expire within the hour. The original is never handed back, and if any step fails, the photo isn't published.

Data walled off in the database

Row-level security keeps a member's private data to that member in the database itself as well as in the app. About 85 tables are tied to each account, so deleting an account removes every row and every stored file it ever created.

Moderation the database enforces

The content filter blocks slurs and self-harm taunts, even with disguised spellings, while swearing and car slang stay allowed. On messages, clubs and profiles it runs as a database trigger, so no screen, old or new, can skip it. Anything can be reported, and every report gets a review.

Security tested against the live app

A suite of 89 security checks runs against the running app as well as the code. Every route is rate limited per member, and if the limit can't be checked, the request is refused.

The booking engine

A calendar that follows the car

A car shows on every day from drop-off to pickup, and cars without dates sit in their own line. Start times fall on the half hour and stop an hour before close, so no job is booked into a closed shop. Job times stay hidden until the shop confirms them.

Prices the server owns

The customer's browser sends only the line items. The server prices them from the shop's own list in whole cents, with rates in basis points, and ignores any total it was sent, so a price can't be changed on the way in.

The 3D Visualizer

Beta

Customers try a tint, wrap or film on a 3D car and send it as a quote request. The server prices it from the shop's list, and anything it can't match goes to the shop as a question.

Running a shop on it

Owners and staff

Owners and staff sign in through separate links. Passwords are hashed with scrypt, only a hash of each session is stored, and the system won't let a shop end up with no active owner.

Inventory with a paper trail

Counts change with a tap, reorder points flag low stock, and every change is logged. The shop is taken from the signed-in session and ignores what the request says, so one shop can't touch another's stock.

A demo in their own name

A shop I'm talking to can try the full product under its own name and logo before signing up. The server decides what's a demo, and a demo never writes, so a sales call can't create a real booking.

Billing

Built, in testing

Shop subscriptions run through Stripe. Every billing event's signature is checked on the server before it can change a plan.

What I learned between the first commit and 98 members

Eight lessons from decisions I made along the way.

Waco, Texas · June 5 to October 24, 2026

Engineering lessons

Constraints decide the design

I was one builder with two app stores to ship to. Three native apps weren't realistic, so I built one web app inside native shells. The push bridge, the test suite and the release path all followed from that one constraint.

Find the limit before you build

My first shop tool tracked inventory, because that's what I assumed shops needed. Watching a shop work showed me the limit was bay time. Four days later the tools were rebuilt around bookings.

Measure before you assume

The live AI service didn't always behave the way its documentation said. I stopped trusting the docs, checked behavior against the live service and wrote the tests around what it did.

Put rules where they can't be skipped

A rule in one screen protects one screen. Putting the content filter in the database means every message, club and profile goes through it, including screens that don't exist yet.

Never let a model grade itself

AI output is checked by code, schemas and tests. When an answer matters, something outside the model decides if it's right.

Show only what's confirmed

Job times stay hidden until the shop confirms them, and a part Smart Add isn't sure about stays separate and doesn't get merged. A wrong answer shown with confidence costs more trust than an honest blank.

Prove the whole path

Two halves that each work on their own don't mean the whole thing works. I check the full path, from a member's tap to what lands on the other side.

Users change the plan

On launch night people used the assistant first, so I built the product around that and changed my original plan.
